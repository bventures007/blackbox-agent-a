# Pilot operations, recovery and answer experience

Owner-approved refinement after baseline-v13. These are binding P0–P4 requirements, not implemented functionality or measured results. Preserve LOCAL-PILOT.md, journal invariants, current tenant/authorization checks and the existing acceptance oracle. This document makes seven previously broad requirements executable; it does not reactivate SaaS, public gateways, native packaging, employee management or an embedded AI platform.

## 1. Backups that users can rely on

Add an owner-only **Backups & recovery** / **Sicherung & Wiederherstellung** area under local settings, summarized in System & Diagnostics. During setup, offer a backup destination outside the live data volume and creation of a separate backup recovery key. Clearly show not configured, scheduled, running, failed, overdue and last successfully created states. The owner can postpone configuration without blocking the first example; this remains an explicit unprotected state. Never silently claim backup protection just because a command exists. Destination enrollment and recovery-key handling use the protected host wrapper; the browser can inspect status or request a backup only to an already enrolled destination through a narrow authenticated action. It cannot accept arbitrary filesystem paths, read host files or execute shell commands.

Default policy after configuration: at least one encrypted backup per 24 hours while the backend is running, plus an explicit backup before a populated upgrade. Schedule before the recoverable-cutoff age reaches 24 hours, with a default 30-minute completion allowance; an overrun is visible as a missed objective, never hidden by changing the cutoff. Keep the latest seven successful daily and four successful weekly generations, sharing the same generation when applicable. A persisted scheduler runs one overdue backup after startup/wake when prerequisites are available, not every missed interval. The user can change the schedule/retention with clear consequences. Record last attempt, last completed generation/cutoff, next due time, failures, destination availability, size and last actual restore-test date. Warn when the newest successful generation is older than 24 hours. An off/sleeping Mac cannot meet that interval; show actual recoverable age instead of promising continuous protection.

Same-device destinations are allowed for convenience but labeled as not protecting against device loss. Recommend an owner-chosen separate volume; detect an unavailable/unmounted target and never silently write to an empty mount-point directory on the system disk. Do not create cloud accounts, upload elsewhere or install an OS service. Retention deletes only completed generations owned by this installation and only after a new generation is finalized; failures cannot remove the last usable backup. Never follow untrusted paths/symlinks out of the selected managed backup directory.

Use a maintained authenticated encryption/container format with a separate public recipient and recovery secret, or an equivalently documented standard envelope design. The wrapper can encrypt scheduled backups using public encryption material; it must not require an owner login session or repeatedly ask for the recovery secret. Create/show the recovery secret through the protected host setup channel, explain saving it separately in a password manager and verify an initial encrypt/decrypt round trip before discarding the transient secret. Do not persist it beside the backup, in its metadata or in logs. It is separate from the owner login key, agent keys and installation data key. Future scheduled creation can verify ciphertext hashes/manifest completeness without claiming that an unattended decryption/restore test occurred.

Back up a coherent database/evidence/key set. Quiesce ingestion, reducers and evidence mutations for the simplest pilot implementation, take a consistent PostgreSQL snapshot/dump and the exact referenced evidence/key material, then release the maintenance fence even on failure. A documented online alternative must prove the same cutoff consistency. Include schema/application/reducer versions, checksums, committed/applied cutoffs, relevant redaction-policy state and the separately protected installation encryption material inside the encrypted bundle. Snapshots/caches are optional acceleration, never the only recoverable business data. Stream encryption or use a protected encrypted staging location; do not leave plaintext dumps on disk. Finalize by atomic rename/publish; interrupted or checksum-failing generations remain visibly incomplete and cannot be selected as valid restores.

`./blackbox backup` creates a generation using the configured destination; `./blackbox restore <backup-path>` is host-only, validates format/compatibility/integrity and requires the recovery secret via a protected prompt/file descriptor, never command arguments. Restore into a fresh isolated destination by default. Preview an explicit destructive replacement before any existing data is changed; no automatic overwrite. Fence restored credentials/sessions before serving HTTP, rotate owner/agent access as already required, and hold provider workers paused until the restored account bindings and policy state are checked. Demonstrate recovery after removing the original installation and its local data key. Losing both backup recovery material and the original usable key is an honest unrecoverable state, not an authentication-reset shortcut.

Recovery objectives: a configured, continuously running healthy pilot targets at most 24 hours of recoverable-data age. This is a schedule objective, not a guarantee while stopped, disconnected or failing. At the smoke corpus with up to 250 MiB of synthetic evidence, target restore-to-authorized-query-ready in at most 600 seconds of measured machine processing; record operator waiting/input time separately and also report full elapsed time. Include decryption, database/evidence validation, required credential fencing and engine recovery. Do not extrapolate this to larger merchant histories or claim provider replay can recover every lost intermediate event. PILOT-01/02 supplement OPS-01 and LOCAL-03.

## 2. Compatible updates and deterministic rebuilds

Add a release compatibility manifest for application/API, worker, engine RPC, MCP bridge, journal/event schemas, reducer/projection/snapshot versions, backup format and supported PostgreSQL major version. Distinguish install-time compatibility from runtime protocol compatibility. Check it before migrations or accepting traffic; unknown/newer incompatible contracts fail with an actionable error rather than coercing data. Keep exact versioned artifacts/image digests and commands available for recovery; no automatic downgrade of populated data.

`./blackbox upgrade` performs preflight (versions, permissions, free space and valid recoverable backup), acquires a single fenced maintenance/migration lease, pauses writers, applies serialized versioned migrations and starts compatible components. Verify health, journal invariants and representative answers before releasing the fence. Show phase/progress/errors in diagnostics; API writes and MCP reads cannot observe a half-migrated or falsely current state. An interrupted upgrade resumes from a durable checkpoint or requires the explicit documented recovery route. A failed backup blocks the upgrade unless the owner deliberately selects a separately verified recovery generation; do not silently proceed without one.

Document rollback support per version. Binary rollback is permitted only when schema, encryption and event compatibility prove it safe. Otherwise use a tested forward fix or an isolated restore of the pre-upgrade generation, displaying its cutoff and any later data loss. Do not promise that reverting an image reverses a database migration. Rerun protection against stale restored access and account identity changes.

Versioned event readers/upcasters interpret old records without rewriting them; unsupported event types quarantine/degrade the affected scope explicitly. New business rules use a separate versioned projection build/checkpoint, compare invariants and publish atomically at a declared cutoff, then catch up new commits. A failed rebuild leaves the last valid interpretation labeled with its version or returns unavailable, never a mixture. Superseding derived assertions append with provenance; replay cannot create duplicate cash, stock or derivation loops. Keep historical interpretation/cutoff semantics visible and reject incompatible snapshots. PILOT-03 adds mixed-version, interrupted-migration and changed-rule tests to OPS-02.

## 3. A safe human repair workflow

Provide an owner-only **Needs review** / **Prüfung erforderlich** list within Sources, linked from affected orders, answers and diagnostic errors. Include quarantined inputs, unresolved entity/payment links, same-provider-ID content conflicts, failed derivations and contradictory source assertions. Show source/account, affected records/questions, the safe original evidence reference, reason, processing stage and available next actions. A technical ERROR is not itself permission to invent a business fact.

Each case has stable tenant/case identity, type, source/run/input references, revision, state (`open`, `in_progress`, `resolved`), safe reason, actor/time history and resolution reference. Operational assignment/retry state may change; business decisions append journal entries. Supported actions are retry processing, confirm/reject a proposed link, append a reasoned correction/manual assertion with its actual evidence, or leave unresolved. Distinguish human-confirmed information from provider-observed information. Never edit the old payload, rewrite provider evidence, delete an obligation, mark a failed import complete or treat an ignored warning as repaired coverage.

Use optimistic revision checks and idempotent commands; competing decisions or repeated clicks cannot double-apply corrections. Owner operations follow existing session/CSRF rules; read-only agents can see authorized business conflict status but cannot repair or approve. Define precedence per field/assertion in the connector/domain mapping; neither newest arrival nor a generic manual flag universally wins. Unresolved financial/quantity ambiguity remains partial/unknown.

Persist a correction/decision and outbox atomically, reprocess only affected entities with existing Rust rules, and expose its required/applied cursor. Show **Decision saved; recalculating** until the new state is published; do not mark a business case resolved before affected query readiness is recomputed. Preserve historical-as-known answers and links to the prior decision. Retry uses the original accepted source identity/deduplication boundary (or clearly identified protected rejected input), not a fabricated new payment. Repeat poison failures stay visible with bounded retries. If retained raw evidence is gone, explain the reprocessing limit rather than inventing it. PILOT-04 proves the whole UI-to-journal-to-Rust-to-MCP repair path.

## 4. Mac runtime lifecycle and storage pressure

Document the current lifecycle explicitly: browser close leaves the supervised backend running; stopping the container runtime or shutting down the Mac stops processing. The pilot starts through the bundled wrapper after the runtime is ready. No automatic login/startup service, keep-awake setting or native menu-bar daemon is installed. Show the restart command and last successful ingestion/cutoff in EN/DE. A later opt-in autostart feature requires its own scope/tests.

Treat sleep/wake, runtime restart, network changes and loss/recovery as normal. Compare persisted wall-clock schedules and monotonic elapsed durations; do not trust timers that fired before suspension. Revalidate leases/fencing and credentials before resuming, replace broken connections, coalesce overdue jobs and perform bounded overlap reconciliation. Respect Retry-After and provider quotas; no burst replay of every missed poll. Do not advance checkpoints on unavailable network or synthesize missed provider events. Test an actual supported Mac sleep/wake plus simulated longer suspension, clock changes and interrupted work. After connectivity/probes return, update local status within the existing diagnostics bounds; source catch-up follows its actual schedule/backlog, with honest gaps and progress. Agent bridges reconnect with current authorization and never replay a revoked grant.

Monitor all relevant filesystems: host destination, container/VM storage, journal/WAL, evidence, staging, snapshots, logs and backups. Default free-space warning is below the larger of 10% or 5 GiB; critical is below the larger of 2% or 1 GiB. Make thresholds visible/configurable with validated positive bounds. Preflight large imports/backups/upgrades using known or explicitly uncertain size estimates. At critical capacity pause new import fetch/ingestion and optional rebuild/export jobs, retain durable cursors and show an action; keep only reads that can still enforce authorization/consistency. Resume when space is safely above the threshold and recheck prerequisites. Actual ENOSPC can precede a sample: failed durable writes must never be acknowledged regardless of the warning state.

Bound staging, parallel downloads, retries, evidence size, query work and caches in addition to the log cap. Record actual finite limits in the implementation configuration and test oversized inputs; unbounded defaults are not permitted. No component may free space by deleting the canonical journal or unrelated files. Logs rotate under their existing policy; raw evidence and backups follow their own explicit policies. A provider-account reconnect validates the same immutable account identity before resuming old cursors. A different account creates a new connection/namespace; it cannot silently replace the history of the previous shop. Disconnecting pauses collection and preserves history with stale coverage. PILOT-05/06 cover lifecycle, reconnect identity and disk faults.

## 5. Secret storage and personal-content boundaries

Create a distinct installation data-encryption key using a maintained CSPRNG at setup. Store it in an owner-only host secret directory (0700, files 0600) outside the database/evidence/backup destination; securely mount only into services that need it. The wrapper/guide documents the actual host paths and ownership, including container UID mapping. Provider/API credentials and sensitive identity/evidence-directory values are encrypted using a maintained authenticated-encryption implementation with unique nonces, key-version metadata and tenant/purpose binding. Do not invent a cryptographic protocol. The exact library/format is selected in a small P0 ADR and validated with real code.

The minimal pilot uses protected files; Keychain integration is optional future convenience, not a native-client prerequisite. Missing/corrupt keys stop dependent operations with an actionable error; never generate replacements over existing encrypted data or fall back to plaintext. OS/volume encryption is recommended for the whole database/evidence storage: do not claim the application encrypts all disk contents or protects against the local OS owner. Owner/agent login keys remain verifier-only and independent of encryption material. Do not inject provider secrets into frontend assets, command arguments, logs or a global environment dump.

Support documented host-authorized data-key rotation with versioned key IDs, transactional or checkpointed re-encryption, read compatibility during transition and verification before old live key material is retired. An interrupted rotation resumes safely. Old encrypted backup generations remain recoverable using their own protected key material; show that retiring a live key cannot magically erase old copies. Provider-token rotation verifies account identity/grants before atomic replacement and respects existing scheduler fencing; failure preserves a truthful recoverable state. The separately encrypted backup contains the installation material needed for disaster recovery. PILOT-07 verifies filesystem access, cipher tampering/wrong-tenant binding, lost-key behavior, rotation and full restore.

Maintain a field-level data inventory in committed schema/connector mappings: purpose, classification, canonical/evidence/directory placement, retention rule, authorized readers and derivation dependencies. Permanent journal payloads contain only allowlisted typed business facts, amounts/units/times, rule versions and opaque local entity/evidence identifiers needed for replay. Keep customer names, addresses, emails, email bodies, attachments and unfiltered provider JSON outside canonical payloads, URLs, deduplication strings and error messages. Provider identity mappings that can identify people belong in the protected scoped directory/evidence boundary; stable journal identity anchors and corrections remain append-only. No simple unsalted personal-data hash is advertised as anonymous.

Default raw-evidence retention is 90 days from local receipt, shown before import and configurable per evidence class/source. A stricter provider/use restriction wins; a longer business requirement needs an explicit selected policy. Historical imports retain their true effective time without expiring immediately just because the business event is old. Explain that facts can remain queryable after the original document expires, while original-content access or a new extraction may become unavailable. This is a product default, not a claim of statutory compliance or suitable retention for every invoice. Canonical replay must work from retained typed inputs without assuming that all original raw payloads still exist.

Expiry/restriction is a guarded workflow: record intent and audit, deny affected content, remove it from live evidence, search/projection content caches and temporary exports, and show unavailable/redacted provenance. Keep numeric business history intact. Persist a separate redaction ledger that is included in new backups and can be exported independently. On restoring an older backup, use the current ledger when available; otherwise keep raw-evidence access blocked until the owner reconciles the restore's policy/cutoff, rather than silently reviving restricted content. Old immutable backups cannot be edited in place: disclose affected generations, expire/destroy them only through the owner's explicit policy and retain evidence of the decision. Do not claim guaranteed erasure of copies already exported or backups outside control. Accidentally embedded canonical personal data still requires an explicit policy/design decision; this contract does not grant normal users UPDATE/DELETE on journal rows. PILOT-08 supplements SEC-02.

## 6. Performance that matters in the first pilot

The strengthened `smoke` profile in ../benchmarks/performance-contract.json is authoritative for the required workload, per-query API/MCP targets, success fraction, memory, lag and recovery bounds. The old two-second mixed-state ceiling remains as a broad regression ceiling; it cannot replace the new hot/cold/history/aggregate gates. Both API and actual MCP framing/auth/cutoff paths are measured. Every result includes current authorization, correct scope and declared cursor, INFO logging and normal durability settings; failures/stale/truncated responses are not fast successes. All active limits apply together under the stated workload. PILOT-09 is a current release gate, not part of the deferred 10m/100m experiments.

Bound business queries to 500 rows/page maximum (default 100), a five-second synchronous deadline and finite per-agent/per-workspace/global concurrency. Initial limits: eight concurrent queries per agent, 16 per workspace and 32 globally; the test driver spreads legitimate 20-client load across the existing 50 synthetic tenants. Explicitly bounded internal work queues and scan/hydration budgets must stop work on deadline/cancellation. Reject excess work with retry guidance; it cannot starve other tenants or consume unbounded RAM. Structured queries exceeding the synchronous budget return an honest unsupported/too-large result with narrower-filter guidance; an asynchronous analytics platform is not required. Keep log-view pagination separate from these business limits.

Record p50/p95/p99, success/retry/timeout fractions, query plan/rows examined, whole-stack/cgroup memory including page cache, cold hydration and disk use. Measure scheduled-arrival-to-completion including queuing, not only service execution. Preserve the same frozen corpus and hardware limits for A/B comparison. Do not mask an overloaded implementation by slowing the test driver, shrinking the corpus or removing source/journal work. Publish observed numbers only after actual execution.

## 7. Clear boundary between answers and language models

The required local **Questions & Answers** view uses all 24 question templates plus typed filters/entity selection and the authorized structured query service. A selected question becomes a versioned intent with validated parameters; display resolved scope, dates/cutoff, evidence, missing data and conflict state. Resolve ambiguous order/customer identifiers explicitly. Results and arithmetic come from the same deterministic Rust/application service used by MCP, never from a keyword lookup or hardcoded demo sentence. Complete EN-default/DE user copy; no model subscription/key is needed for this built-in path.

General free-text conversation is initially supplied by the user's separately configured local MCP-capable agent/client. Explain that distinction and provide a tested connection/copyable question flow. A cloud-only agent still cannot reach loopback by itself. A UI free-text field may search/select templates or entities only if clearly labeled as such; do not present it as an unrestricted AI chat. Do not silently forward queries/business content to an LLM or require a hidden hosted model to pass local installation/tests.

An embedded LLM/chat service and automatic email extraction are not required to complete this pilot. Their existing conditional security gate remains applicable if implemented, but this refinement does not authorize adding them by default. Generic/replay communication records can exercise the domain without a real mailbox adapter or AI extraction. Document supported templates versus additional composable MCP queries, model/client compatibility and external data flow. Read-only tools cannot guarantee the wording of a third-party model's answer; they must provide correct bounded data, evidence and explicit limitations and label external content as untrusted. PILOT-10 verifies the model-free path, no silent network egress and the actual agent handoff.
