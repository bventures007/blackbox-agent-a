# Historical import, first connection and data readiness

> Current delivery: LOCAL-PILOT.md. This import/readiness contract remains required for the local browser and MCP bridge. Native/remote/gateway displays apply only if a later scope enables those modes. The automatic local workspace has one owner; read-only agent keys exercise denied import controls. No employee-management or public-hosting flow is needed.

Binding owner-approved behavior for the initial connection, ongoing source management and evidence-backed answers. Implement with SOURCE-SYNCHRONIZATION.md, WEBHOOK-GATEWAY.md, JOURNAL-AND-MCP.md and the question-data contracts. All engineering material is English. Browser and desktop product copy is English by default with complete German localization. These are requirements, not implemented features or completed provider tests.

## 1. Product defaults and explicit user choices

Default to **the last 30 days plus accessible older open items and their necessary related records**. Start new-event collection concurrently with the historical import, using the durable overlap protocol; do not wait for all history to finish before capturing new activity. Make the application usable progressively, with truthful per-question readiness. Never promise a fixed import duration or complete historical coverage before checking the source.

Use this first-connection flow:

1. Connect and validate account identity, authorization, grants, permitted use and available historical capabilities. A successful credential check is not a completed import.
2. Show the workspace's proposed date range and a plain-language explanation of older open/related records. Offer **Last 30 days** (default), **This year**, **Last 12 months** and **Choose a start date**. Put **From now on** under advanced options. Show the resulting actual dates and timezone. Display known restrictions before import starts; an unsupported request must not silently become a shorter successful import.
3. Review scope and start. Persist a versioned import plan, who selected it and when. A workspace has one suggested history start; newly connected sources inherit it as a proposal. Show and record source/capability overrides and actual availability separately. A later connection must not reset the workspace's original start to a new rolling 30-day window.
4. Show resumable progress and let the user enter the product while import continues. Prioritize new activity, open/relevant items and recent records; schedule older history with bounded resources and provider-rate fairness. Offer useful questions as soon as their required fields, links and projections are ready; do not require unrelated sources to finish.

At confirmation, resolve relative presets once into a fixed start and initial-import cutoff. Last 30 days means a rolling 30 x 24-hour interval ending at that cutoff; show exact local times so the interval is unambiguous. This year begins at January 1, 00:00 in the workspace timezone. Last 12 months uses calendar-month subtraction with an explicit end-of-month clamp. A custom date begins at local midnight in that timezone. Store the selected IANA timezone and resolved UTC interval `[requested_from, initial_cutoff)`; reject invalid/future dates and test daylight-saving boundaries. Ongoing ingestion follows the cutoff with overlap/deduplication; this window does not advance as a daily deletion rule. Timezone changes do not silently reinterpret a saved plan.

For **From now on**, show a separate, explicit choice to include current opening state and older open items. Explain that those may reveal older business records. Do not import old records behind a strict new-data-only choice. If opening data/context is declined or unavailable, balances and questions depending on it remain partial/unknown. Later context expansion requires a visible scope change, not an invisible widening of consent. Minimize unrelated customer/document data.

## 2. A date is a business scope, not one universal created-at filter

Each capability declares which source timestamps select relevant records (order date, transaction date, invoice date, scan date, effective date or another verified field). Distinguish source occurrence, last modification, local observation and local recorded time. A current update to an old order is still new activity; a refund in the requested interval may require an order/payment created before it. Do not drop it because the parent order predates the window.

In addition to the selected interval, include the following within the disclosed/authorized scope and actual provider access:

- Accessible older open orders, unpaid/part-paid invoices, outstanding shipments, unsettled payments/payouts, unresolved returns/refunds/disputes, commitments and reservations needed for the supported Order-to-Cash questions. Define open/closed semantics per capability; an archived UI flag alone does not prove all financial obligations are settled.
- The minimum older parent records, line items, captures, credit notes or other evidence required to interpret selected/open records. Follow stable tenant/account/entity links. Bound relationship traversal and expose unresolved dependencies; never crawl unlimited unrelated history without user intent.
- Available opening state: for example stock quantities, reservations, open receivables or provider balances with their exact scope and as-of time. An opening snapshot is not a new sale, cash receipt or stock movement. Apply the existing snapshot-versus-delta rules and preserve conservation; never use a current balance as an earlier opening balance without evidence.

If permissions, API history, retention/use conditions or missing identifiers prevent coverage, show the affected capability, actual accessible period, missing dependencies and an actionable remedy where available. Do not claim that all older open records were checked when only a recent slice is searchable. Where current snapshots exist but original transitions do not, preserve the observation as a snapshot and keep history completeness unknown/partial.

Historical facts are appended when learned, with their original effective/source time only where supplied. Their local `recorded_at` is the actual import time; never backdate system knowledge. Label backfilled history separately from activity observed during ongoing collection. Do not synthesize an order's intermediate status changes from its present status. Existing source caveats remain binding, including Shopify historical-order permissions and DHL permitted retention/use; selecting a year does not waive them. Validate the current API/product/account, not a provider-wide assumption.

## 3. Persisted run and coverage contracts

Implement typed shared DTOs, database migrations and query-service contracts from these logical fields; these are not a demand for a particular physical table count. Tenant scope and role checks apply throughout. Operational progress can be mutable; the business journal remains append-only. Keep bounded audit history of plan changes, imports, retries and user actions.

| Import plan | `plan_id`, `plan_revision`, `tenant_id`, `connection_id`, capability scope, `preset`, `timezone`, `requested_from`, `initial_cutoff`, `include_open_items`, `include_related_records`, `include_opening_state`, actor/time, source overrides, provider/API revision, known availability/permission/retention restrictions. Explicitly record the strict from-now-only choice. |
| Import run | `run_id`, plan revision, `run_kind` (`initial`, `history_expansion`, `incremental`, `reconciliation`), state, phase, started/updated/completed times, provider cursor/checkpoint, attempt/retry and lease identity, per-capability scope, counters, errors, next action and resulting coverage/checkpoint references. Retries retain logical run identity and audit attempts. |
| Coverage slice | Tenant/connection/capability, requested and actually checked scope, relevant timestamp semantics, `history_kind` (`event_history`, `snapshot_only`, `mixed`, `unknown`), historical coverage (`complete_for_declared_scope`, `partial`, `unknown`, `unavailable`), verified intervals/holes, fields/event families covered, linked-dependency status, as-of/checked time and journal/applied cutoffs. Derive from actual query dependencies and authorized data, never from the number of green source cards. |

Store coverage as separate intervals/capability slices when needed. Do not turn two successful checks or the first/last record into a claim of complete time coverage. Preserve plan/run identity and progress across window close, process restart and browser refresh. A stale cached status includes its observation time and must not pretend to be live. Runtime health belongs to each tenant/account; it is not derived from the development register's approval status.

## 4. Progress that users can understand

Show four recognizable stages: **Check connection → Import records → Link and process → Ready for queries**. These phases may overlap across capabilities; show each source's current work and explain partial availability. The underlying synchronization states from SOURCE-SYNCHRONIZATION.md remain authoritative. Distinguish complete, complete-with-gaps, paused, failed and canceled runs; completion of fetching is not completion of processing.

Expose requested dates, available dates, run phase, discovered/fetched counts, committed records, query-ready records, pending work and failures, grouped by meaningful record type. Count logical records using stable identities, not HTTP attempts or emitted journal entries: one order may produce many journal entries and retries may fetch the same order again. Query-ready counts refer to the same declared record cohort and projection requirements as their denominator. Keep duplicate/skipped/failed outcomes separate; a filtered or quarantined record is not automatically ready. Counts and labels must reconcile without mixing objects, pages, bytes or event counts.

Use percentages only when an exact total for the named cohort/stage is known. Unknown totals show counts, phase, elapsed time and ongoing activity, not fabricated percentages. Estimated totals are explicitly estimates and do not generate an exact completion percentage. Fix initial-import totals to the run cutoff; show live events separately. If discovery revises the scope or dependencies, expose the revised total/scope instead of silently changing what a percentage means. Do not average stage percentages into a misleading overall completion number. A clearly named fetch stage may reach 100% while processing remains pending; that must not be presented as overall readiness. No overall 100%/ready label while required processing, links or coverage checks for that claimed scope remain unresolved.

Example: **8,200 orders loaded; 7,900 ready for order queries. Payment import is still running.** This does not mean 7,900 orders have complete payment answers. Show that dependency separately. Do not promise an ETA without a defensible measured estimate. Ensure counters are refreshed from durable server state, not a frontend timer.

Provide role-authorized pause/resume, retry and history-extension controls where supported. Pausing a historical job must not silently pause live collection; display the scope of each action. Canceling an import preserves committed journal entries and shows the remaining gap. Resumption and repeated actions cannot double-count business effects. Errors identify the affected source, retained progress, next retry/action and relevant user-facing explanation without secrets. A resolved source error is separate from a repaired historical gap.

## 5. Three places for the same trusted state

### First connection

Use the existing friendly onboarding/source setup design. Show plan choices and limitations before starting, then persistent progress, usable questions and remaining prerequisites. The application must remain navigable; no blocking full-screen spinner until the entire history is finished. Initial results may be partial and must say so. Both English and German must cover date selection, counters/plurals, stages, errors, gaps, accessibility labels and action consequences.

### Central Sources page and source details

Keep this inside **Sources**, not a separate tracking product. The overview shows every connected source with account identity, initial-import/current/delayed/paused/error state, last completed import with outcome/scope, last successful scoped synchronization, last received/new event, delivery mode and polling cadence or event-driven label, next scheduled check, pending processing, import progress, actual historical coverage and limitations. Prioritize actionable degraded/blocked sources without concealing other sources. Do not collapse a partial payment capability behind a green orders capability on the same source card.

Source details provide per-capability history/import runs, exact timestamps/timezone, requested versus available dates, permissions, coverage gaps, last attempt/error, reconciliation state, received/committed/applied milestones and safe recovery controls. Offer retry/import-more/history inspection; surface missing provider permissions with a concrete next step. Keep sensitive credentials, raw errors and tenant data appropriately scoped. Relative timestamps have an accessible exact timestamp; status is not communicated by color alone. Show an unavailable/unknown value as such, not as a fabricated date or zero.

A successful complete empty poll advances the scoped last-successful-sync time but does not advance the last-new-record time. A failed/partial poll or credential test cannot advance the successful full-scope sync time; partial progress updates only its verified slices. Quiet providers can be current after successful checks; receiving a webhook alone does not prove that all other events arrived. Track periodic reconciliation independently. Push-only sources with no completeness check show that limitation. For event-driven/manual/internal sources, explain why a next poll does not apply rather than inventing one.

Derive delayed/degraded states from configured capability-specific polling/reconciliation schedules, permitted lag and actual progress; record thresholds. A single global green light or arbitrary interval is insufficient. Runtime/health observation failure itself produces unknown/stale status after a documented bound. Display observed delivery/processing latency only from valid timestamp pairs, with a period/sample basis and clock limitations; distinguish observed latency from configured cadence. No fixed speed or end-to-end freshness guarantee follows from the last receipt timestamp.

### Every answer, including MCP

Use the same backend readiness/coverage service for source screens, browser/desktop answers and MCP. Attach an accessible summary of sources used, last successful scoped checks, requested/actual answer period, remaining import/processing and missing data. Provide details/evidence links without requiring a separate admin page just to understand the result. For a question with required data still unavailable, return `partial` or `blocked` and explain what must finish/connect; do not fabricate zeros or silently omit unmatched records. An unrelated unfinished source must not block a fully supported question.

`ready` means supported for the declared query scope/cutoff and freshness contract, not absolute business truth or complete external history. `latest_committed` does not mean latest external event. Honor fixed answer snapshot/at_least_cursor semantics while new import batches commit; health metadata must not claim a newer applied state than the answer used. Separate historical completeness from current synchronization. Gateway received, journal committed and Rust applied remain distinct. Missing opening state blocks balance/absence claims that depend on it. A valid query with zero results can be ready only when relevant coverage justifies that absence.

## 6. History expansion, viewing, memory and retention

Import period, default analysis period, RAM working set and retention policy are independent. A Last 30 days dashboard filter is a view preference; it never deletes journal entries or changes the connector's saved start date. The bounded Rust working set prioritizes active/recent/open items regardless of age and hydrates cold history through indexed PostgreSQL reads. Do not promise that a full selected year resides in RAM.

Let an authorized user extend history later after a preview of availability, approximate volume where knowable and limitations. Persist a new plan revision and a resumable `history_expansion` run; preserve prior verified coverage. Concurrent live ingestion and retries deduplicate across overlapping intervals. A newly discovered older event must not regress current state or turn a snapshot/opening balance into a second financial movement. Keep original effective time and actual later recorded time so historical-as-known answers remain reproducible. Reevaluate affected links, projections and question readiness as new evidence commits.

Reducing an analysis window does not erase history. Narrowing future collection scope, if supported, is an explicit audited action with its consequences; it must not silently drop follow-up events for already tracked open obligations. Raw evidence retention/redaction follows the existing approved policy and provider rights separately; this specification does not authorize journal deletion or override retention obligations. From-now-only, unavailable history and removed permissions stay visible in every affected answer.
