# Identity, access and recovery

Binding owner-approved requirements for M0–M5. This contract replaces the earlier four-role and mandatory password/OIDC wording. It specifies a product to implement, not an existing authentication service. Read with WEB-DESKTOP-AND-DEPLOYMENT.md and JOURNAL-AND-MCP.md.

## 1. Product experience and deployment independence

Use passkeys for human server sign-in and protected device enrollment for convenient local use. The backend must provide authentication and authorization without a mandatory external identity provider, mail service, commercial authentication subscription or Blackbox-operated control plane. Select maintained WebAuthn, session and OAuth components, pin versions and document the integration in an ADR. An additional self-hostable auth process is acceptable if required by the chosen maintained solution. Do not invent a cryptographic login protocol.

| Situation | First use | Subsequent access |
| --- | --- | --- |
| Local Mac, browser or desktop | Host-authorized setup creates the local administrator, enrolls this device and explains recovery; no email/password registration form | Open directly using the enrolled device or existing protected browser session. Re-enrollment/recovery is explicit if access was revoked or the credential store is unavailable |
| Own server | Obtain a short-lived setup code through the protected host/installer channel, claim the first administrator and enroll a passkey | Passkey sign-in using a supported device authenticator or security key |
| Hosted SaaS | Enroll a passkey and create a new isolated workspace, or accept an explicit invitation | Passkey sign-in, then select only a workspace with active membership |
| Desktop connected to a remote server | Open the system browser for that server's normal authorization flow | Use a scoped remote session; local device enrollment grants no rights on the remote server |

Public servers require HTTPS and explicit trusted origins. A loopback-only local profile may use the supported localhost secure-context exception with exact origin/Host checks and protected pairing; any LAN exposure needs the normal TLS/server sign-in profile. Verify the actual browser/library behavior. Do not silently relax cookie, origin or WebAuthn checks when a profile is incompatible.

A passkey is a public-key credential scoped to the relying party (RP), not a username or a reusable setup code. The server stores the public credential and a stable internal user ID, not its private key. Device passkey synchronization is optional and controlled by the user's ecosystem; a hardware security key must remain an alternative. No mandatory Nostr identity, phone account, email verification or passkey-sync vendor. Optional future password, email-link or OIDC modes need a separate design and security acceptance; they are not first-release requirements or recovery shortcuts.

## 2. Minimal actor and permission model

Keep two workspace roles for humans: `owner` (display label Owner / Administrator) and `reader` (read-only employee). Do not implement a redundant mandatory Member/Admin role hierarchy. A workspace can have multiple owners, must retain at least one active human owner, and must support an explicit ownership handover. Service principals are a separate principal type with explicit read grants, never human owners. The SaaS platform operator is a separate administrative context, not a third workspace role.

| Capability | Human owner | Human reader | Agent/service principal | Platform operator context |
| --- | --- | --- | --- | --- |
| Read journal/state/history and authorized answer evidence | Workspace business access | Within current read grant | Within current read grant | No implicit business access |
| Read sensitive raw evidence / export business data | Explicit authorized owner operation | Only if granted | Only if granted | No implicit access |
| Configure sources, import scope and business settings | Yes | No | No | No implicit tenant management |
| Invite/remove people, create/restrict/revoke agent grants | Yes, with recent verification for sensitive changes | No | No | No implicit tenant membership |
| Become owner or broaden own permissions | Existing owner grants it after verification | No | Never | Never through ordinary operator APIs |
| Edit/delete canonical journal history or issue financial MCP actions | No | No | No | No ordinary product endpoint |
| Configure hosting plans/quotas and platform operations | No, unless separately an operator | No | No | Yes through separate operator authorization and audit |

Account identity, workspace membership, client authorization and credential are distinct. Removing one workspace membership must not delete the person's other memberships. An employee using only MCP still has an individual human identity and membership; dashboard use is optional. Every unattended agent has its own service principal, named responsible human owner and grants. No shared team bearer token, owner-session reuse or service-principal promotion to administrator.

The host/database administrator remains an infrastructure trust boundary. Do not promise that a person controlling the server cannot access its database or keys. Any deliberate support/break-glass access must be a separate time-bounded, justified and audited operation; it must not be an invisible operator bypass. There is no default SaaS support impersonation feature.

## 3. Grants and enforcement through the entire read path

Every authorization result binds the authenticated principal, backend issuer, workspace, current membership/grant revision, allowed tools/read operations, allowed canonical input datasets, sensitive-evidence permission and export permission. Use stable dataset IDs from question-data-contracts.json and explicit permissions for additional journal families. Unknown/new tools and datasets are denied until granted. The grant editor can offer a simple “All current business data” preset with its concrete covered set visible. A new connector may supply additional records in an already allowed dataset; explain that this grant covers that dataset across sources. It cannot silently grant additional datasets/tools or raw-evidence/export privileges. Source-specific restrictions are not implied by a dataset grant.

For the first release, restrictions are by workspace, dataset/tool and raw-evidence/export permission. Arbitrary customer-level, order-level or field masking is not promised. Show this boundary clearly when creating access. Each workspace has a separate grant even if one person belongs to several. Effective access is the intersection of active membership, grant, client authorization and token scope; a requested scope or tenant_id never creates authority.

Enforce the same policy in API, MCP, UI services, exports, evidence/object downloads, source health, jobs serving user requests, Rust RPC/hot memory, cached responses and PostgreSQL cold/history reads. Keep real production-role RLS and tenant-scoped keys as an additional boundary. Carry validated authorization context from trusted services; reject client-supplied internal scope and protect internal engine ports. Do not accept an arbitrary tenant ID merely because an OAuth token is valid.

A restricted caller cannot infer excluded data through aggregate totals, derived answers, search snippets, readiness counters, provenance links or an export download. An answer whose calculation depends on unauthorized inputs must return a safe permission-limited result, without exposing hidden values or sensitive existence details. Derived projections need dependency-aware authorization; filtering the displayed evidence list after calculating from all data is insufficient. Cache keys include authorization context/revision as well as workspace and query cutoff. Long-running exports and pagination recheck current access before delivery. Sensitive download access must have a revocable authorization check rather than an unrevocable long-lived public object link.

“All authorized business records” still covers all five journal tracks and histories beyond the 24 example questions. It never includes credentials, authentication/session/recovery tables, operator secrets or other workspaces. Read-only agent credentials cannot call signed generic ingestion, source configuration or native host-control endpoints. Provider ingestion, generic producers, workers and gateway consumers use separate least-privilege internal/connection identities and are not a loophole in the read-only agent model.

## 4. Safe bootstrap and remembered local access

Server setup is a one-time privileged transition, not “first visitor becomes admin.” An explicit host installation/setup action generates at least 128 bits of random setup-secret entropy, displayed only through a protected local channel, hashed at rest, limited to setup, expiring after 30 minutes and atomically consumed once. Repeated, concurrent, expired and guessed claims fail. No code in public logs, analytics, repository files or URL query strings. Throttle attempts. Registration must finish and establish recovery before the setup transition completes. Disable the setup endpoint after successful initialization; restart or an empty business workspace must not reopen it. Any reissue requires an explicit host-authorized action and invalidates the old code.

Hosted self-registration can create a new workspace under platform signup/quota policy; it cannot claim an existing tenant or platform-operator rights. Normal self-hosted deployment is invite-only after first setup. Email address is optional contact metadata unless separately verified; matching an email address never grants workspace membership. Anonymous registration and setup must be covered by anti-abuse/rate-limit tests.

Provision the platform operator separately through a protected deployment action with passkey authentication and its own role/context. Creating a workspace owner never creates a platform operator. Public endpoints must not expose a way to claim operator privileges through tenant setup.

Local use enrolls a device to the local human owner through a one-time host-authorized exchange. The local launcher/CLI may obtain this enrollment through the protected installer channel; the public loopback API cannot mint it for an arbitrary caller. Store the long-lived Mac device credential in the OS Keychain and only its verification material/hash server-side. Exchange it for revocable backend sessions through the selected maintained auth components. Keep browser pairing codes one-use, at least 128 random bits, with a five-minute maximum lifetime and an exact intended origin/session; no permanent bearer secret in localStorage or a printed URL. Opening an already paired browser/desktop should feel immediate. A new browser profile requires a deliberate pairing action, not automatic owner access based on loopback.

The core comparison checkpoint must provide secure CLI/browser setup and pairing without the native app. M5 adds the native integration with the same backend identity model. On non-Mac hosts, document and test the selected protected host-credential mechanism; a file-based Linux secret must have explicit ownership/access controls and cannot be a web-readable project file. A locked or unavailable Mac Keychain gives a clear recovery/unlock state; never silently export a plaintext fallback. Revoking a device prevents silent re-enrollment on its next API request. A deliberate host-authorized reset remains possible because host ownership is a separate trust boundary.

Test exact allowed origins/Host headers, CSRF, DNS-rebinding attempts, remote navigation and forged pairing exchanges. Other origins and local processes without credentials do not automatically become the owner. Do not claim isolation from malware already controlling the same OS account or key store. A local session, device credential or helper never authenticates a remote backend and never grants arbitrary native process execution.

## 5. Passkeys, sessions and invitations

Use maintained WebAuthn verification for challenge freshness/single-use, expected origin, RP ID, credential/user binding, signature and required user verification. Support compatible synced passkeys and security keys; do not incorrectly reject all synced credentials because counters are not strictly increasing. Record the chosen counter/backup-state handling in the security ADR. Never accept an assertion for another RP, registration flow or account. Security-sensitive changes require a recent authenticated verification (maximum age five minutes) or the narrowly scoped recovery procedure. This includes owner changes, new access grants, recovery-factor changes and new credentials.

Recent verification means an interactive passkey/user-verification ceremony or, for a local enrolled device, a tested native OS user-verification mechanism bound to the operation. Silent refresh or a background exchange of the remembered device secret is insufficient. The core browser-only path must support passkey verification or protected host-authorized confirmation without depending on the future native shell.

Web sessions use opaque revocable identifiers, HttpOnly cookies, secure production cookie attributes, deliberate SameSite behavior, session fixation protection and CSRF defenses for writes. Do not put session/refresh credentials in browser localStorage. Default public-server sessions have a 30-minute idle timeout and a 24-hour absolute lifetime; deployments may choose shorter limits. Local remembered-device enrollment can open a fresh local session without a recurring login form; do not confuse that enrollment with a permanent non-revocable session. Desktop remote authorization uses the system browser, authorization code with PKCE and an exact validated redirect; store remote refresh material in the OS credential store.

Invitations bind one workspace, intended role/grant, inviter, expiry and usage state. Default to reader access; owner invitations need recent verification and an explicit privileged invitation. Use random single-use tokens (at least 128 bits, hashed at rest, 24-hour default expiry), atomically consumed. To avoid mandatory email infrastructure, support an owner-copied invitation. If recipient identity cannot be verified beforehand, acceptance enrolls/signs in the recipient and creates a pending membership that the inviter confirms against that identity before any business access. An already-known intended user can be bound directly. Do not treat an unverified email/display name or possession of a leaked invite link alone as verified identity. Forwarded, wrong-account, replayed, expired and revoked invitations must be tested. No automatic invitation sending without a configured service and explicit user action.

## 6. Individual MCP access for people and agents

For a human MCP client, use the pinned supported MCP HTTP authorization flow: discovery/protected-resource metadata, authorization code with PKCE, passkey browser authentication and explicit consent to the client/workspace/read grant. Show the same access in People & agents. Validate issuer, intended resource/audience, redirect, state, expiry and scope; grant membership is checked independently of OAuth consent. Consent cannot upgrade a reader or service principal to owner. Avoid token passthrough and issuer/client mixups. Use refresh-token rotation/reuse detection when refresh tokens are issued.

For unattended agents, create a separate service principal and per-client credential. Use standards-based client credentials to obtain short-lived scoped access tokens where the MCP client supports that extension; support a securely provisioned client secret or maintained private-key assertion mechanism. Prefer a private-key assertion where supported. Pin and test the selected library/extension and actual client versions. Client registration/discovery behavior must match those versions. No assertion that every named agent/client supports every flow; document a tested compatibility table and actionable unsupported states. Lack of one commercial client account does not excuse missing protocol tests.

Default access-token lifetime is at most five minutes. OAuth expiry alone does not satisfy revocation: the current principal/membership/grant/credential state is enforced with the bound below. Display service credentials once on creation where applicable, store only hashes/verifiers for inbound secrets, keep private keys client-side and support overlap-limited rotation. Source-provider tokens needing later use are encrypted with separate keys; do not store all secrets with a single inappropriate hashing strategy. Never embed an owner's password/passkey material or browser session in MCP configuration.

Local stdio or a local bridge shares the same authorized read services and an explicitly selected principal/grant. Credential material is obtained through protected configuration/OS storage; being a child process or running on localhost is not blanket owner authority. A webhook gateway only transports source events and does not make local MCP reachable from a cloud client. Public reachability and authentication are separate requirements.

## 7. Recovery, revocation and ownership continuity

First-owner setup must offer an additional passkey and issue one-use recovery codes with an explicit save/acknowledgment step. Local users must establish a recovery route before onboarding is marked complete; a device credential alone is not a recovery plan. Recovery codes have at least 128 random bits each, are shown once and stored only as hashes with use/revocation state. Never log, export through MCP or retain their plaintext. Adding a second authenticator and regenerating codes require recent verification; regenerating invalidates the old set.

Recovery is a rate-limited, time-limited, restricted session that can enroll a replacement authenticator and revoke compromised access, not immediately read business data or create broader grants. Consume a recovery code atomically and prevent concurrent replay. Complete verification of the new authenticator before issuing a normal session. Account recovery preserves existing memberships without adding any, invalidates existing human sessions/refresh tokens and compromised device/passkey credentials, and offers an explicit review/revocation of separately owned service credentials. Lost-device and sole-owner recovery must be documented and tested. Without any valid factor/code, a self-host operator can follow a separately authenticated, logged host recovery procedure; there is no anonymous server reset. A hosted user cannot claim host privileges by requesting support. Do not invent an automatic email-only recovery fallback.

Protect the last active owner against removal/demotion/deactivation, including concurrent requests. Removing an owner requires transfer of responsibility for active service principals or their revocation, so no orphaned agent remains. Workspace membership removal revokes that person's workspace grants and active workspace sessions/authorizations; it must not erase canonical business history or unrelated workspace access. Removing one passkey/device must revoke sessions attributed to that factor/device; provide an explicit revoke-all option.

Revocation/downgrade acknowledgment follows a durable authorization-state commit. New requests must observe it immediately on the processing instance; distributed authorization caches must expire/invalidate within **60 seconds maximum**, including after restart/failover. Fail closed if a replica cannot establish current authorization within that bound. Apply the bound to API, MCP, active streams, exports, object downloads, hot/cold queries and refresh/token issuance; recheck before each new page/chunk or operation. Cancel pending delivery of affected results and close/re-authorize affected streams within the bound. Already delivered information cannot be recalled; do not claim otherwise. Revocation must not wait for a long-lived token or open connection to expire.

Record actor, workspace, target, action, timestamp, result, reason where applicable and correlation ID for enrollment, sign-in/recovery, invitation/consent, permission changes, credential rotation and revocation. Log safe metadata only. Security audit records are append-only and tenant/operator-scoped; authentication state itself is mutable and separate from the five business tracks. Report actor identities and credential IDs without recording secret values.

## 8. Storage and migration contract

Implement explicit logical storage for the following; physical schema/SQL belongs in the implementation ADR and migrations:

| Record | Required meaning and representative fields |
| --- | --- |
| Human identity / passkey | user_id, status; credential_id, user_id, public_key, rp_id, verification/backup metadata, created_at, last_used_at, revoked_at |
| Workspace membership | workspace_id, user_id, role (`owner`/`reader`), status, revision, inviter, timestamps; unique pair and last-owner invariant |
| Service principal / read grant | principal_id, kind, workspace_id, responsible_owner_id, display_name, status; grant_id, tools, dataset IDs, evidence/export flags, revision, expiry |
| Session / client authorization | opaque session verifier, user/principal, device/factor, issuer/client/resource binding, workspace grant, idle/absolute expiry, refresh family/reuse state, revoked_at |
| Device / service credential | credential_id, principal/device binding, secret verifier or public key, purpose, scopes, expiry/rotation state, created_at, last_used_at, revoked_at |
| Setup / pairing / invitation / recovery | purpose-bound hash, issuer/subject/workspace binding as applicable, expiry, single-use/consumed state, pending confirmation where needed |
| Security audit | immutable event ID, actor, workspace or operator context, target/action/result, UTC time and correlation; no secret payloads |

These are operational/identity records, not additional business tracks. Global authentication tables are private to the auth component and unavailable to tenant query/runtime roles; tenant-owned memberships/grants/audit use proper tenant constraints and policies. Generic auth-library tables must not become an accidental RLS bypass. Revocation checks must remain consistent through snapshots/restarts, and restoring old backups must deliberately invalidate/rotate stale sessions and credentials so revoked access does not silently revive.

Choose an explicit restore strategy in the ADR: reconcile against a trusted newer authorization/revocation state, or keep restored access fenced and require protected host-authorized re-enrollment/rotation before reopening it. An old backup cannot establish which credentials were revoked later. Old recovery codes are also stale credentials; do not recover a restored server by trusting an old code alone when later revocation state is unavailable.

Migration to another backend/RP origin requires explicit credential handling. WebAuthn private keys are not exported by Blackbox and a passkey for one RP does not automatically authenticate another. Re-enroll through an authenticated one-time migration/recovery process, bind the new issuer/workspace, and invalidate old sessions/tokens/device bindings. Scope per-tenant migration: never export a multi-workspace user's global credentials, other memberships or unrelated auth state into another customer's server. The new target may need a newly enrolled identity linked to the migrated workspace. Keep provider/gateway credentials, human identity, agent grants and native host authority separate throughout.

## 9. Management UI and evidence for completion

Add **People & agents** to workspace settings, integrated with the existing Agents & MCP page. English default and complete German localization follow the common policy. Offer “Add person” and “Add agent” with a short name, target workspace, explicit read permission preset/details and connection instructions. Adding a person defaults to reader; privileged owner access is a separate deliberate choice. Keep complex OAuth terminology in optional setup details rather than the main journey.

Show access type, responsible owner, active/pending/revoked status, allowed data/tools, evidence/export permission, creation/expiry, last actual use and revoke/rotate actions. “Never used” is distinct from missing telemetry. Include invitations, sessions/devices, passkeys and recovery status, without exposing secrets or other tenants. Reader accounts can manage their own authenticators/sessions but cannot change workspace permissions. Explain exactly what the chosen client can connect to and access. A protocol example or UI simulation is not a connected agent. Use the supplied visual style for the new views; these screens are not already implemented in the reference.

M0 records the auth choice/threat model and role/grant contracts. M1 implements core bootstrap, passkeys, local CLI/browser pairing, people/grants/recovery and two-tenant enforcement. M3 implements human/service MCP authorization and compatibility evidence. M5 completes native Keychain UX, real Mac authentication and safe migration/restore. The earlier checkpoint requires core browser/protocol security tests; it cannot defer authentication until native packaging. A virtual WebAuthn authenticator proves tested browser flows, not a real Touch ID/security-key/platform result.

Implement AUTH-01 through AUTH-12 plus existing MCP/WEB/DESKTOP/DEPLOY/SAAS gates. Test meaningful misuse and races against actual sessions, database roles and hot/cold read paths, not only mocked policy functions. Record actual commands, commit, environment/client/authenticator versions and observed outcomes in reports/acceptance.json. These specification cases remain not_started until executed. Private customer accounts are unnecessary for the core tests; actual Mac/authenticator and external MCP compatibility proof are separately identified.

## Standards and comparison context

- [WebAuthn specification](https://www.w3.org/TR/webauthn-3/): RP-bound public-key credentials and authenticator verification. Pin supported behavior at implementation time.
- [MCP authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization) and [client-credentials extension](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials): separate resource authorization and client-dependent machine access; a normal web login alone is insufficient.
- [Buzz security](https://github.com/block/buzz/blob/eafd77e9f6e96052476bdd88be732c046fdb7ab3/SECURITY.md) and [architecture](https://github.com/block/buzz/blob/eafd77e9f6e96052476bdd88be732c046fdb7ab3/ARCHITECTURE.md): reviewed as comparison material for self-hosted identity, signed authentication and separate membership. Blackbox uses the passkey/OAuth contract above; it does not inherit Buzz's protocols or assert Buzz's implementation was independently security-tested.
