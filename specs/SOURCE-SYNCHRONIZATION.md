# Source synchronization contract

Binding for every source/data capability, in all deployment profiles. The central work list is INTEGRATIONS.md; its machine-readable plan/history and committed mapping artifacts remain the authority for implementation evidence. A provider logo is not evidence of API, polling or webhook support.

## Per-capability transport declaration

For each `provider.dataset` row, investigate and record the pinned API/product revision, account prerequisites/grants, exact resources and event topics, public callback registration/rotation/removal method, initial history window and pagination, incremental cursor semantics, polling/filter limitations, reconciliation route and rate budget. A provider may support push for orders but only polling or no access for payouts. Do not inherit an entire provider's mode support onto all rows.

The register's `transport_plan` contains three investigation obligations, not verified support. A committed implementation mapping must add `synchronization` with:

- `initial_import`, `cursor`, `reconciliation`, `deduplication`, `freshness`: concrete rules, with explicit reasons for internal/import paths where a remote poll does not apply.
- `modes`: exactly `local_standalone`, `local_gateway`, `public_server`. Each has `status` (`supported`, `partial`, `unsupported`), `methods` (from `polling`, `direct_webhook`, `gateway_webhook`, `import`, `internal`, `authenticated_push`), `schedule`, `history_limit`, `authentication`, `recovery`, `limitations` and `reason`. Use strings describing actual behavior, never an unexplained "N/A".
- `schedule` specifies the actual default interval, adjustable bounds, jitter/rate budget and reconciliation frequency where relevant. For event/import-only paths specify the trigger and recovery check. No invented universal 30-second promise: select defaults from current provider constraints and measure observed freshness.
- `limitations` identifies lost intermediate changes, unavailable fields/events, retention, account coverage and unavailable recovery. Supported means the declared subset works; it never implies a complete provider history. Partial modes must expose the missing subset. Unsupported modes have no methods and a concrete reason.

Local standalone cannot use provider webhooks addressed to localhost. Local gateway can use `gateway_webhook`, not `direct_webhook`; public-server mode uses `direct_webhook`, not `gateway_webhook`. Polling/import/internal paths may apply in any profile. `authenticated_push` describes a producer that can actually reach the backend; it is not a loophole for an unreachable provider callback. The signed generic API can be submitted locally; a remote producer needs a public callback path. Bank CSV remains an import, replay/rules/runtime remain internal producers. Roadmap providers remain unverified and outside launch scope.

Every mode must be covered by the contract tests, including refusal/explanation for unsupported modes. Pipeline, recovery, tenant and applicable live tests cover every supported/partial mode for that capability. Test records carry `modes` and case IDs; separate artifacts may be summarized in one immutable evidence record. Reviewers explicitly acknowledge unsupported modes as well as missing fields/events. Contract tests are not live-provider evidence.

## Lifecycle and durable state

Expose explicit connection states: configured → validating → backfilling → catching_up → ready, with degraded, paused, reauthorization_required, blocked and disconnected states. Keep mode and per-capability coverage separate from overall connection status. An empty successful response is not automatically a complete history.

1. Validate credentials, account identity, grants, data-retention permission and callback feasibility. Resolve OAuth authorization/redirect URLs separately from webhook URLs. OAuth may use a supported loopback redirect, a tightly scoped public broker or a documented provider-specific flow; do not assume that all providers allow local redirects or that the event gateway implements OAuth. Use state/PKCE and bind the connection server-side. Mark unsupported onboarding explicitly.
2. Establish a durable overlap boundary before initial import. Register/buffer callbacks first where appropriate, or save a provider-supported cutoff/cursor and overlap the subsequent poll. Fetch all pages with bounded concurrency. Avoid a gap between backfill and live collection.
3. Commit a page's accepted observations and progress atomically, or use an idempotent resumable page protocol. A failed/partial page must not advance its checkpoint past unseen data. Track initial import separately from incremental/reconciliation progress. Provider cursor, gateway queue receipt and canonical committed cursor are different identifiers.
4. Poll outbound from the backend/worker, never from a browser tab. Use provider delta cursors or updated-time filters where trustworthy; add overlap and stable pagination. Deduplicate durable business identity across poll, webhook, replay and retries. Preserve conflicting payloads as evidence; do not overwrite a prior journal record.
5. With direct webhooks, validate the actual provider authentication and connection identity, size/content limits and exact raw signature input. Durably commit the canonical Source observation and transactional processing outbox before successful core receipt acknowledgement. If this cannot fit the provider deadline, use the explicitly separate durable gateway/inbox protocol with its weaker transport-receipt status; never label a queued receipt as a canonical commit. Append derived tracks after deterministic normalization. Reject invalid inputs and retain visible quarantines for accepted poison payloads.
6. Reconcile periodically even when push is available. Missing webhooks, disabled subscriptions, cursor expiry, scope changes and history truncation must be visible. Refetch current resources and available histories using the documented coverage window. A current snapshot cannot reconstruct every missing intermediate event. Record source/effective time, observed time, recovery provenance, gaps and affected question uncertainty; never invent transitions or claim a lossless history.
7. On restart resume persisted cursors/checkpoints, recover leases and reconcile the elapsed interval. Use one active logical scheduler per connection/capability via leases/fencing, with tenant fairness, backoff/jitter, Retry-After, bounded queues and cancellation. Live mode changes do not reset identities or double count; overlap old/new paths safely and then retire the prior registration.
8. Pause/disconnect stops future collection, unregisters owned callbacks where possible, revokes access, and declares treatment of queued deliveries. Failed unregister/revocation is visible with retry guidance. Do not delete committed business history. Credential rotation must not strand valid pending receipts or route them to another tenant.

Mutable synchronization tables store tenant/connection/capability, selected mode, provider revision, backfill and delta/reconciliation cursors, interval configuration, leases/fencing tokens, grant status, last attempt/success, next attempt, coverage bounds, pending count, failures and subscription identity. Mutable gateway delivery/operational state is separate from immutable business journal entries. Timestamp observations never replace a committed journal cursor for consistent reads.

## Honest health and answers

Both clients show backend location, selected delivery mode, callback/gateway state, last successful source check, next scheduled poll, oldest pending receipt, backfill progress and known coverage gaps. Separate **received by gateway**, **committed in journal**, and **applied by Rust**. A quiet provider or successful gateway HTTP response does not prove complete freshness. Keep source freshness, transport backlog and engine lag independently observable.

The shared API/MCP query result exposes scoped coverage, last successful source synchronization, pending/gap reasons and committed/applied cutoffs. `latest_committed` means the latest commit in this workspace's backend, not the latest possible external provider event. Gateway receipt IDs cannot satisfy `at_least_cursor`. Unknown/partial must propagate to affected business answers, including absence claims. Successful imports do not certify later provider activity.

Required acceptance: SYNC-01 through SYNC-04 plus INGEST-01 through INGEST-06, PERF-02, QUERY-02, REGISTRY-01 and gateway tests. Launch accounts/access remain external prerequisites; preparing these contracts does not automatically connect a source.
