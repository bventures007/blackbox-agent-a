# Independent identity and resumable data-key rotation

Fresh local installations create independent random 256-bit data and identity keys. Stable opaque connector IDs use the identity key. Owner/agent verifiers, internal RPC/cursor material and the separate age recovery identity keep their existing independent purposes.

Encryption uses Node's maintained AES-256-GCM implementation with fresh 96-bit random nonces, 128-bit tags, and authenticated tenant, object/purpose and key-version context. The evidence envelope identifies its version and key ID; provider envelopes use version 2 JSON. Legacy version 1 evidence and provider envelopes remain readable. A bounded protected keyring names one active version and at most one pending version. SHA-256 integrity fingerprints of the random data/identity keys reject accidental replacement by different same-length bytes before startup, encryption or identity derivation. These are corruption checks, not protection from an OS owner who can replace both keys and metadata. IDs map to fixed validated filenames, never arbitrary paths. There is no plaintext fallback or replacement of lost material. Evidence writes fsync the ciphertext and containing directory before journal acknowledgment.

`./blackbox key rotate` holds the host operation lock and stops API, worker and engine. A protected checkpoint records the prior service state and durable cutoff. Each evidence ciphertext is independently authenticated against the immutable plaintext hash; provider credentials are decrypted with their tenant/connection binding. Re-encryption is atomic per file and conditional per credential row. A second complete verification precedes the active-key switch, old live key removal and audited service restart. An error leaves the runtime fenced. `./blackbox key resume` reasserts the fence, skips verified target-version objects and continues. If interruption happened after service restart, newly accepted target-key writes are included in re-verification. Runtime identities cannot invoke maintenance or receive key material through MCP.

The independent identity key is unchanged. Completed backups contain their own declared data-key version, identity key and keyring within the age-encrypted envelope; a backup is refused during an incomplete rotation. Removing a live key does not erase keys contained in older backups, filesystem snapshots or storage remnants. No SSD erasure claim is made.

Early development installations used the data key for opaque identity derivation. Silently replacing that derivation would fork entity identities; retaining the same bytes as an identity key would falsely claim retirement of the old encryption secret. These legacy installs remain readable and explicitly refuse data-key rotation pending a deliberate legacy migration. Their original backups preserve the original derivation when restored. The supported fresh installation path uses independent material from its first input. This development compatibility limit does not waive PILOT-07 for the released pilot.

Verification is recorded in the checkpoint. Unit tests alone do not establish interrupted live database rotation, restore, complete policy retention or independent acceptance.
