# Release compatibility and migration identity

`release/compatibility.json` distinguishes installation schema/PostgreSQL from runtime protocols and persisted formats. Current implementation: 0.1.0-pilot.5, schema12, input reader2, outbox processing2, lifecycle-v3 with retained v2 interpretation, records-v3 and questions-v9. PostgreSQL17 is the Compose installation; PostgreSQL18 is allowed only for the native development harness. No filesystem snapshot format is claimed.

All twelve migration files and checksums are bound by the manifest; earlier migrations are immutable. Fresh initialization and each later migration commit their exact ledger entry under an advisory lock. Runtime roles cannot migrate or change the contract. Host, API, worker and Rust require the complete exact ledger and active runtime before traffic. Internal RPC and MCP require the matching fingerprint in addition to existing authentication. Changed/partial/newer histories, unknown compiled protocols and maintenance fences fail closed. A fingerprint is a format agreement, not authorization or a package signature.

Populated upgrades accept exact schema8,10,11 sources and same-schema12 image replacement. The explicit host upgrade pins actual image IDs, probes each compiled manifest, takes one maintenance lease, stops writers, authenticates a coherent pre-upgrade backup, checkpoints every additive migration, compares representative retained interpretations and streams a complete journal digest. Only successful verification starts traffic. Failed lifecycle generations require a separately recorded exact build retry; candidates and audit history are retained. Current runtime13 or any other unlisted schema remains unsupported.

Authenticated backups retain exact schema5/6/7/8/10/11/12 readers. For schema5/6, restore checks the complete observed SQL schema, ACLs, RLS, constraints, triggers and function bodies against pinned fingerprints. Only generated pg_dump header/footer metadata is normalized. Any checksum ledger must match its exact immutable prefix. Pre-ledger attestation uses `observed_legacy_schema`, never invented historical execution. Known historical runtime fingerprints are checked independently, including schema11's original fingerprint after schema12 adds its reader/processing metadata. Remaining migrations run only within isolated fenced restore. Recovery creates new access credentials and retains evidence/provider restrictions.

Schema12 adds operational quarantine/retry bounds and an indexed unsupported-input guard. Prior lifecycle projections without reader metadata cold-replay; incompatible runtime components cannot join the new installation. Unknown accepted formats fail explicitly. A normal upgrade currently requires the source engine to drain its outbox; compatible host forward repair for an already blocked unsupported-format workspace remains unfinished and must not be described as verified.

Clean schema8/10-to11, same-schema11, archive recovery and failed-build retry evidence remains at `reports/runs/generations-71972d2` and `reports/runs/projection-retry-5c7f7ee`. Schema12 actual upgrade/recovery evidence follows implementation; unit checks alone do not certify it. Versioned downloadable distribution, full performance and independent approval remain open.

Validation: `python3 -m unittest discover -s scripts/tests`, `npm test`, `npm run typecheck`, `CARGO_HOME="$PWD/.runtime/cargo" cargo test --locked --offline -p blackbox-engine -p blackbox-domain`. Actual populated upgrade uses `scripts/verify-populated-upgrade.py` with an exact own-repository prior bundle and recorded Node/Rust image IDs; it preserves failures, exercises interruption/resume, and restores the authenticated pre-upgrade archive separately.
