# Release compatibility and migration identity

`release/compatibility.json` distinguishes the supported installation schema/PostgreSQL major from runtime protocols and persisted formats. It names application/API, worker, Rust RPC, MCP, journal/events, lifecycle/typed/question rules, projections, evidence/provider envelopes, keyring and backup versions. There is no separate filesystem snapshot format to certify. PostgreSQL17 is the supported Compose installation; PostgreSQL18 remains compatible only with the existing native development harness.

The host validates every migration file and its checksum before initialization or restoration. Fresh initialization applies the foundation and its ledger entry in one transaction; each later migration and ledger entry shares another advisory-locked transaction. Migrations001–006 remain unchanged. Migration007 adds global installation metadata containing no tenant business data. Runtime roles have SELECT only on the contract and migration ledger; the maintenance identity alone can change them.

Host startup requires the complete exact migration ledger and active runtime contract. API, worker and Rust independently perform the same check before serving requests or processing jobs. Unknown formats, changed checksums, partial/newer histories and a persisted maintenance fence fail closed. API/worker check the engine's declared contract before starting. Internal Rust RPC requires the matching contract fingerprint as well as its existing secret and tenant/principal authorization. The MCP bridge sends a contract fingerprint and checks the response fingerprint inside its existing request deadline. The wrapper waits for a matching API readiness response before reporting successful startup and stops application services on readiness failure.

The fingerprint is a format agreement, not an authentication credential or signature. It does not replace caller authentication, package/image integrity, journal verification or authorization. Each implementation pins its supported runtime-format fingerprint; editing the manifest to invent support cannot bypass that check.

Restore validates schema5/6/7 metadata inside the authenticated archive. For schema5/6, it compares the complete observed schema-only dump, including ACLs, RLS, constraints, triggers and function bodies, against a pinned known fingerprint before migration. Only generated pg_dump version comments and restrict/unrestrict tokens are removed. Schema5 is checked again as schema6 after the known additive recovery-guard migration. Unknown legacy structures stay fenced.

A pre-ledger database receives checksum rows with `observed_legacy_schema` provenance only after that whole-schema comparison. This records current schema compatibility, not a claim that historical migrations were executed or recorded. Existing checksum histories must match the expected prefix. The new runtime-contract migration then runs transactionally and all gates are rechecked. Current-format backups preserve their actual ledger. Restored business access still gets new credentials and raw-evidence/provider restrictions.

Historical images and copied preview directories remain unchanged. New gates deliberately reject their missing metadata; normal startup never performs an implicit populated upgrade. An existing installation requires the explicit fenced upgrade workflow or a verified fresh restore. At this increment, the upgrade command, interrupted-upgrade resume, versioned projection publication, package digest manifest and complete PILOT-03/OPS-02 evidence are still being implemented. The manifest and startup checks alone do not complete those requirements.

Verification commands: `python3 -m unittest discover -s scripts/tests`, `pnpm test`, `pnpm typecheck`, and `CARGO_HOME="$PWD/.runtime/cargo" cargo test --locked --offline -p blackbox-engine -p blackbox-domain`. Actual verification uses the fresh `scripts/verify-packaged-mcp.py` stage followed by `scripts/verify-release-compatibility.py --stage-record RECORD --output REPORT`, original-loss recovery, and separately authenticated legacy backup recovery. Clean results and limitations are recorded in reports; unexecuted commands are not evidence.
