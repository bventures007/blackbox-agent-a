# Shopify fulfillment observations

The optional local Shopify fulfillment capability uses Admin GraphQL 2026-10 with the existing verified shop and orders read grant. It reads order update ranges and accessible older open/unsettled context from immutable import plans. The source remains synthetic-tested; live account access and independent review are unavailable.

Order.fulfillments is an array, not a cursor connection. The query therefore omits its optional first limit, checks the exact fulfillmentsCount against the whole returned array, rejects duplicate fulfillment identities and bounds each order to 1,000 fulfillments. Nested fulfillmentLineItems are cursor-paginated through the fulfillment query, checked against the same updatedAt and bounded to 500 lines. Missing/repeated cursors, imprecise counts, response overflow or a changed header fail without accepting truncated coverage. A fetched outer page permits at most 10,000 aggregate fulfillment lines, including nested pages. Outer order pages contain at most ten orders; a run permits at most 10,000 pages, with the shared 2 MiB response and 45-second page limits.

The fulfillment ID gives a connection-scoped economic identity; order, location and line IDs use the same opaque namespace as other shop facts. The observation revision is the provider updatedAt, not a content hash. Repeated identical revisions are idempotent; changed content at the same revision is quarantined. Quantities are exact nonnegative integer pieces, with no null-to-zero conversion. Duplicate line assignment is rejected. Created, updated, handover and delivery timestamps must have consistent order and cannot exceed the fixed scan cutoff.

SUCCESS alone means preparation. Only inTransitAt establishes a recorded handover; deliveredAt establishes recorded delivery. A delivered observation does not manufacture a missing handover time. Administrative cancellation is retained separately and never erases supplied handover/delivery. Preparation or failure without physical milestones produces a valid fact and an explicit fulfillments.handover_confirmation coverage gap. It produces no goods movement. A later real milestone can resolve that gap. Invalid quantities or contradictory timestamps remain quarantined.

Rust records physical handed_over/delivered assertions on fact, movement and reservation tracks; other states remain facts. The typed derivation version is records-v2. These are versioned assertions sharing the stable economic record ID, not additive stock deltas. Queries select the current record once; replay, administrative updates and delivery do not add the same shipment quantities again. Current stock is never inferred from these observations. Later provider snapshots that erase or change recorded physical milestones or line quantities are quarantined for explicit correction; they cannot silently undo known goods movement. Preparation gaps also derive from retained canonical facts, so a later empty population check cannot erase them. The immutable older track assertions remain available for recorded/effective cutoff reconstruction.

Coverage is a declared order-scoped point at the fixed import cutoff. Missing physical milestones, rejected objects or a declined historical context cannot certify that point. The adapter does not claim a complete shipment event stream, carrier scan population, parcel-to-line allocation or worldwide shipment population. Carrier and tracking identifiers are not yet collected by this adapter; carrier tracking requires a supplemental source. Empty current fulfillment lists are observations, not evidence of physical returns or historical nonexistence. Original encrypted evidence is limited to one fulfillment and the minimal order header. Strict selection excludes declined older fulfillment content from both canonical facts and retained evidence.

The existing durable page cursor, lease/account/reconnect fencing, encrypted credentials, source health, independent polling/reconciliation chain and bounded retained-input retry apply. Retry preserves the original immutable plan and cutoff and does not certify the entire provider population. The UI offers this capability explicitly and explains the handover limitation in English and German.

Run `python3 scripts/verify-fulfillments.py --output .runtime/fulfillments-evidence.json` with the isolated native developer runtime running. It exercises actual synthetic HTTP, PostgreSQL, Rust, API, SDK MCP, browser scope selection, process restart with an unapplied page and deleted-projection recovery. Tracking coverage in the quantity fixture is supplied by an explicitly separate synthetic generic producer; it is not credited as Shopify carrier verification. Formal release, performance, live-provider and independent-review gates remain separate.
