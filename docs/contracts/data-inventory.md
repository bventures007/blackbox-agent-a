# Field inventory and privacy boundaries

`data-inventory.json` records the current executable implementation. Each entry has a purpose, classification, storage placement, retention rule, authorized readers and derivation dependencies. References to the policy dictionaries are part of each field's definition. Pseudonymous UUIDs and integrity hashes are linkable information, not anonymization.

The inventory includes all 260 leaf fields of the canonical record/lifecycle/observation contracts, all 117 selected response fields of the six implemented Shopify capability queries, and all 269 PostgreSQL base-table columns. Additional entries describe authorization responses, credentials, encrypted cursors, operational JSON, developer replay input, original evidence and host material. SQL JSON columns point to canonical contracts or explicitly named operational boundaries. A wildcard for original provider/legacy content is intentionally classified as potentially sensitive; it does not authorize copying that content into canonical history. This is not a claim that every possible original document has a known schema.

Canonical history keeps strict typed facts for the installation lifetime. Original bytes use separately enforced receipt-based retention, permanent shortening, provider ceilings when explicitly configured, and audited disposal. Old backup copies have their own retention and availability limits. Source credentials and paused-job cursors have operational lifetimes; they are not covered by an asserted 90-day automatic erasure policy. Session cookies can persist in the browser; server verifiers enforce expiry, idle limits and revocation independently. The recovery identity belongs in an owner's separate private copy, outside both live storage and backups.

Run `npm run validate:inventory` after any contract, mapping or reviewed source change. It compares actual canonical JSON schemas, actual query selection paths and hashes, reviewed source fingerprints and the exact migration manifest. The ordinary Node test suite also runs this gate and adversarial drift checks. Changes require reviewing purposes, mappings, storage and dependencies, not just regenerating hashes.

For an installed test database, set the protected `ADMIN_DATABASE_URL` environment through the existing host/runtime tooling and run `npm run validate:inventory -- --database`. This additional read-only check compares observed base-table names, columns, types and nullability without reading or emitting row values. The isolated native developer runtime supports `python3 scripts/native-dev.py exec node --import tsx scripts/data-inventory.ts --database`. Database columns alone do not prove nested JSON semantics or authorization correctness.

The six implemented Shopify capabilities are orders, payments, refunds, stock, fulfillments and allocations. Live merchant permission and permitted retention remain unresolved. Selected returns/receipts, Shopify Payments, bank CSV and dedicated policy/customer replay onboarding still have explicit pending boundaries. Add their actual field mappings as implementations land. Technical diagnostics currently have per-component limits; the required global seven-day/100-MiB policy, temporary debug and full operational proof remain separate work. Inventory validation is neither live provider verification nor independent acceptance approval.
