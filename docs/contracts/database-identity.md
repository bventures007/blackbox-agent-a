# PostgreSQL installation identity

The supported host wrapper binds each new installation to its protected Compose project, exact local volume, PostgreSQL 17 cluster system identifier and database OID. Explicit setup creates `.runtime/database-identity.json` (owner-only mode 0600) after verifying the new database is empty and before issuing an owner key. Repeated setup preserves the same identity.

Before starting application traffic, the wrapper validates the volume's Compose ownership labels and reads its control files through the pinned PostgreSQL image with no network, a read-only volume, an unprivileged user, dropped capabilities and bounded resources. Missing/corrupt control files, foreign labels, missing markers, different clusters and replaced databases fail closed. Only the PostgreSQL service starts for the live identity check; API, worker and engine startup follows verification. MCP checks the existing cluster without starting it. Docker daemon failures are errors, never evidence of an empty install.

Backup, backup-fence recovery and key rotation use the same checks under the installation maintenance lock. A database verification failure leaves application services stopped and retains the maintenance checkpoint. A backup failure handler cannot restart an unverified database. Status, logs and ordinary stop remain available without the marker or key material (an outstanding maintenance fence still requires its own recovery procedure).

If the original volume is missing, `./blackbox up`, `setup` and `reset-access` do not create a replacement. Restore a verified encrypted generation into a new destination with the separately saved recovery key; use the documented restore procedure. The fresh target gets its own cluster marker before loading the archived schema. The source marker is deliberately absent from backups: it identifies a physical cluster, not portable business data. Restore still revokes old credentials and keeps raw evidence/provider work fenced.

Never edit a marker to accept an unexplained replacement. Restoring the original protected marker and original volume is valid; independently verified backup recovery is the alternative. Historical development previews without a marker are not automatically adopted. Keep their recorded runtime intact to create a backup, then use isolated restore with the current bundle. This check protects against accidental loss/replacement; a host administrator controlling Docker and every protected file remains outside the runtime trust boundary. Direct Docker/Compose commands bypass the supported wrapper and are operator-only diagnostics.

Verification: eight deterministic fault-state tests cover unavailable/foreign volumes, corrupt control output, cluster/database replacement, missing/unsafe markers, empty initialization and backup recovery fencing. `scripts/verify-bootstrap.py` exercises marker loss/mismatch against actual PostgreSQL; `scripts/verify-backup-recovery.py` removes only its own new synthetic volume, proves three host entrypoints do not recreate it, then restores into a different cluster and checks authorized API/MCP answers. These expanded integration checks passed at clean3900f66; recorded commands, exact images and limitations are in `reports/runs/database-identity-3900f66`. No complete operational/distribution gate is implied.
