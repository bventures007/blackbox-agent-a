1. PRODUCT AND VISUAL CONTRACT
Blackbox is a business flight recorder for commerce. It connects source systems, records evidence and changes, derives business state, and exposes consistent, permission-aware answers to the UI and external agents through MCP.

Preserve the reference's green/cream visual language, dark sidebar, typography hierarchy, dense event tracks, evidence drawers, friendly source setup, landing page and Agent & MCP page. Build reusable React components and design tokens. The reference's compressed JavaScript, static answers and browser-only persistence are not the production architecture.

Required areas: landing page; sign-in and first-run setup; workspaces and memberships; recorder; source catalog and connection health; business questions; Agent & MCP settings; searchable/exportable event history; basic administration, retention and audit information. Keep the 24 Order-to-Cash questions and their six groups. The application UI and landing page default to English and also provide complete German localization, with persisted language preference. Engineering material remains English. Dates, currencies, time zones and quantities must be formatted deliberately.

DHL, DPD and UPS are ordinary sources feeding the common recorder. Do not add a separate shipment-tracking product area. Xentral has been removed and must remain absent. Klaviyo is an optional later connector, not a required launch dependency. Existing connector cards may remain only with honest states: available, configured, syncing, degraded, unsupported or planned. A mock must never be labeled as a live connection.

2. ONE PRODUCT, THREE DEPLOYMENT MODES
Use the same domain model, migrations, authorization rules and release artifacts for:
(a) hosted multi-tenant SaaS;
(b) a customer's own Linux server;
(c) local use on a Mac, including Apple Silicon.

Self-hosted mode may start with one workspace, but must not bypass tenant isolation. Do not create separate local/SaaS business implementations. The application and replay tests must function without a commercial cloud account or an LLM key. Real external connectors still require network access and the appropriate provider accounts.

Local installation means a browser application running locally through Docker Compose, not a required native Mac app. A native wrapper can be a later product. Remote webhooks cannot reach localhost by magic: document polling where supported and opt-in HTTPS forwarding for development. A sleeping Mac cannot continuously collect events; catch-up after restart must work and freshness must be visible.

3. DEFAULT ARCHITECTURE
Use a TypeScript/Rust monorepo: pnpm workspaces for the web/API/connector layer and a Cargo workspace for the deterministic business/query engine. specs/PERFORMANCE-ARCHITECTURE.md is the binding performance, consistency, memory and recovery contract. Default stack:
- React + Vite for the application and a static/prerendered landing page.
- Fastify for the HTTP API and production static-asset serving.
- A separate TypeScript worker entrypoint for source transport/orchestration.
- A Rust engine owning canonical business reducers, incremental projections, compact bounded in-memory indexes and business queries; API/MCP share its versioned authorized service contract. No duplicate financial reducers in TypeScript.
- PostgreSQL as the authoritative durable journal and transaction store, with persistent projections/checkpoints and indexed cold-history access; Drizzle plus reviewed SQL migrations. RAM is rebuildable acceleration, never an independent source of truth.
- PostgreSQL-backed jobs, preferably pg-boss, with transactional inbox/outbox boundaries and idempotent handlers.
- Official maintained MCP SDK for a read-only server mounted in the API and an optional local stdio entrypoint using the same application services.
- An established maintained authentication implementation supporting local accounts and an OIDC adapter. Select and pin it in an ADR. Verify remote MCP OAuth interoperability separately; ordinary web login alone is not sufficient. Use supported OAuth/resource-server libraries, not custom cryptographic protocols.
- ObjectStore interface: local persistent volume by default, S3-compatible storage for hosted installations or multiple API replicas.
- Rust unit/property tests for canonical reducers/query behavior; Vitest for TypeScript services/contracts; real PostgreSQL integration tests, Playwright for browser acceptance and the required performance harness.

Use supported stable dependency versions at implementation time and commit pnpm and Cargo lockfiles. Record versions and licenses. A change to the default stack needs a short ADR explaining measurable benefit for both SaaS and self-hosting, not a cosmetic preference.

Build one logical modular product with explicit interfaces, independently runnable API, worker and Rust engine. Initial deployment should require API/web, worker, the engine and PostgreSQL; include a maintained auth service only if the selected implementation needs it. A reverse proxy is part of the public-server profile. Do not require Kubernetes, Kafka, Redis, a vector database or a proprietary SaaS control plane for the first release.

4. EVIDENCE AND EVENT MODEL — THE CORE OF THE PRODUCT
The binding data-structure, append-only enforcement and MCP read-coverage contract is specs/JOURNAL-AND-MCP.md. Implement it as part of M1–M3; the journal is not merely an optional audit log.

Keep the five visible tracks: Sources, Facts, Commitments, Movements, Reservations. They are linked views of a shared evidence graph, not five unrelated databases and not five numbers added together.

Persist source observations and raw evidence separately from normalized events and rebuildable read models. Every business event needs at least: internal ID, tenant ID, connection ID, provider/account namespace, provider event identity or documented dedup key, entity references, schema version, event type, occurred_at, recorded_at, provenance/evidence references, and correlation/causation IDs where applicable. Facts record derivation rule/version and their input evidence. Time values are UTC internally with source-time information retained where meaningful.

Use explicit entity links for customers, orders, lines, invoices, shipments, transactions, refunds and payouts. Email addresses and coincidentally identical order numbers are not globally unique join keys. Record ambiguous links and conflicts instead of silently merging them. Two tenants can have identical external IDs.

The canonical journal is append-only: runtime roles cannot UPDATE, DELETE or TRUNCATE committed entries or their immutable payload/link records. Corrections, reversals and releases append linked entries, preserving original assertions. Enforce this at the database boundary and test the actual roles. Mutable projections and operational state are separate and may be updated or rebuilt. Minimize personal content in the journal; authorized retention/redaction applies to separately stored sensitive evidence with an appended audit entry and explicit unavailability. Any requirement to purge personal content mistakenly embedded in the journal needs an explicit design decision; do not silently relax append-only protection. Privileged database/host operators are a separate trust boundary, not a claimed tamper-proof guarantee. Raw payloads should be access-controlled, size-limited and encrypted where appropriate. Never log access tokens or complete private email bodies.

Store integer minor currency units with currency, and explicit decimal quantity/unit types. Do not use floating-point money. Do not sum currencies without an explicit dated conversion rule. Separate snapshots from deltas, and authorizations from captures, credit notes from cash refunds, provider payouts from bank credits, physical stock from reservations, and promised deliveries from received goods.

Support current and historical queries with explicit time semantics: occurred/effective time versus what the system knew at recorded time. Late or reordered observations must not regress current state simply because they arrived last. Provider versions/order guarantees and reconciliation snapshots must be considered. Expose conflicts, gaps, connector coverage and last-successful synchronization.

Structured connector data should use deterministic mapping. Optional email/document/LLM extraction must produce candidates with source quotations, confidence and review status; uncertain extractions must not silently become authoritative monetary or stock facts. Treat source text as data, never as agent instructions.

5. TENANT AND ACCESS BOUNDARIES
Model tenants/workspaces, users, memberships, role assignments, connections and service credentials. Start with Owner/Admin/Member/Read-only and explicitly scoped MCP service access. Validate membership server-side. The client choosing a workspace or sending tenant_id is not authorization.

Every tenant-owned database table uses tenant_id and appropriate tenant-scoped constraints, composite references and indexes. Enable PostgreSQL RLS with read/write policies, enforce it for application roles, and use separate migration credentials. Application and worker data roles must not own protected tables or have SUPERUSER/BYPASSRLS. Prove the actual production roles are subject to policies. A privileged queue dispatcher, if needed, must not expose tenant data and must establish a validated scope before domain work.

Pass tenant scope through API, worker, MCP, search, exports, files, caches, retries and audit access. Use transaction-local tenant context and prove connection-pool reuse cannot leak scope. Derive webhook tenancy from authenticated connection identity and signature verification, not from a payload's tenant field. Tokens are hashed or encrypted appropriately, scoped, revocable and redacted from logs. Credential encryption keys live outside the database with documented rotation and recovery.

Use maintained session/password/auth components, secure cookies, CSRF protection where applicable, login throttling and tested account recovery. SaaS self-registration/invitations and local first-admin bootstrap must not create default passwords or unauthenticated administration. Specify session revocation and permission-change behavior.

6. INGESTION AND CONNECTORS
Implement a connector contract covering configuration schema, supported capabilities, credential test, initial backfill, incremental cursor/checkpoint, webhook verification, normalization, reconciliation, rate limits, retries, health and disconnect/revocation. Declare actual data coverage and provider API revisions.

Receive and durably record verified deliveries before acknowledging them. Use transactions/outbox so a crash cannot acknowledge an event and lose its processing job. Assume jobs and deliveries may execute more than once. Enforce deduplication and side-effect idempotency in persistent storage; no blanket end-to-end exactly-once claim. Support retries with backoff, dead-letter inspection, safe retry, pagination, resumable backfill and catch-up after downtime. Reconciliation is mandatory; webhooks alone are insufficient.

Build in this order:
A. A documented signed generic-event API, deterministic replay connector, and validated bank-statement CSV import. These make the complete Golden Scenario reproducible without credentials. They must use the real persistence, ingestion, authorization and projection paths.
B. Shopify read-only order/fulfillment/inventory ingestion and Shopify Payments financial ingestion for the initial Shopify-focused product. Discover the actual permissions, account eligibility, IDs and API capabilities from official docs. Do not count a Shopify Payments transaction again if a Stripe view represents the same payment.
C. One real invoice provider (default easybill) and one real carrier (default DHL), including explicit order/entity linking. Confirm actual API availability before implementing; list any merchant contract or account requirements. If a required capability is unavailable, complete the adapter work that can be validated and mark the unavailable capability honestly. Do not silently substitute simulated data.
D. Remaining source cards from the reference are extension roadmap entries until implemented and verified: Shopware, other invoice tools, PayPal/Mollie/Stripe as independent provider accounts, DPD/UPS, mailbox integrations and optional Klaviyo. Their full live implementation is not part of the first release contract.

Use real-shaped sanitized fixtures and mock HTTP servers for connector contract tests, plus separately recorded live/sandbox smoke tests. Without credentials, the correct status is implemented + contract-tested, live verification pending. It is not production-certified.

7. QUESTIONS AND MCP
Build deterministic query services for the six Order-to-Cash areas and all 24 supplied questions. Queries return: answer/status, calculation where relevant, exact evidence IDs, effective/recorded cutoff, freshness/coverage, missing inputs and conflicts. If a prerequisite is absent, return an explicit unknown/insufficient-data result. Do not return the same canned paragraph merely because a keyword matches.

Acceptance must include changed amounts, quantities, IDs and timestamps beyond the included examples. Evidence links must resolve within the caller's tenant and permissions. The UI and MCP must call the same services.

Implement search_events, get_business_state, get_evidence and the schema-discovery, complete journal/history traversal and bounded structured-query capabilities defined in specs/JOURNAL-AND-MCP.md. The 24 question intents are a required minimum, not an access boundary: agents must be able to inspect all authorized business records across all five tracks and compose additional supported queries. Define input/output schemas, stable snapshot-based pagination, limits and stable errors. Do not expose arbitrary SQL, unrestricted file access or a write/payment action in the initial MCP surface.

For remote MCP, implement the current supported HTTP transport and OAuth resource-server requirements, discovery, issuer/audience validation, expiry, scopes, tenant binding and revocation using maintained libraries. Pin the tested protocol/SDK versions. Test at least one real compatible client plus a protocol-level client when access is available. For local stdio, share services and keep credentials out of source control. If a named client cannot be tested, document that limitation instead of claiming universal compatibility.

An external agent may summarize returned facts or draft a response. Core balances and provenance must still work without an LLM. A native in-app AI chat is optional; the required product is a trustworthy recorder/query service, not a model subscription.

9. INSTALLATION, HOSTING AND OPERATIONS
Deliver a versioned multi-stage container build for linux/amd64 and linux/arm64, a Compose release profile using tagged images, and a source-build fallback. Run as non-root where practical. Do not deploy a development or Vite preview server as production.

Provide an actual ./blackbox command wrapper with documented commands: doctor, setup, up, down, status, logs, demo, verify, backup, restore and upgrade. The wrapper must check prerequisites; it must not silently install system software or require a commercial cloud account. Local binds to loopback by default; public-server profile uses HTTPS/reverse proxy with explicit configuration. Generate secrets securely, preserve persistent volumes, and never run down -v or destructive resets as part of ordinary startup.

A first-time user should be able to install prerequisites, run ./blackbox setup and ./blackbox up, open the printed local URL, create the first admin and start the example workspace. This is a target acceptance experience, not an existing command in the supplied reference.

Provide Linux server deployment instructions, environment variable schema, external PostgreSQL and object-store configuration, tenant onboarding, per-tenant ingestion quotas, liveness/readiness, structured redacted logs, queue lag/dead-letter and sync-staleness metrics, database/migration status, graceful shutdown and credential rotation. Hosted scaling uses stateless API replicas, shared storage, tenant-aware workers and partitioned Rust engines with explicit ownership, applied-cursor routing and failover. Do not load every tenant into every API/engine replica. Scale based on measurements and indexes, not a claim that containers imply unlimited capacity.

Backups include database, evidence objects and recovery of encryption keys/configuration. Implement and actually rehearse restoration into an isolated environment. Rehearse upgrading one prior schema version with populated data; use a documented compatible rollback or forward-recovery path. Do not assume a down-migration is safe. Document maintenance windows and measured recovery time/data-loss window; do not promise high availability from a single VM.

Keep SaaS platform subscription billing distinct from customers' order payments. Initially allow operator-managed plans/quotas; commercial self-service billing, tax/legal documents and provider marketplace approvals are separate launch decisions, not silently invented functionality.

10. TESTING AND EVIDENCE
Implement executable tests derived from ACCEPTANCE.json and the Golden Scenario, plus independently designed adversarial variations. Include:
- Domain invariants and property-based variations for money, quantities, supersession and replay.
- Integration tests against real PostgreSQL, actual RLS roles and actual worker/job paths.
- Signed/invalid webhook, duplicate/concurrent delivery, late events, rate-limit, cursor resume and failure recovery tests.
- Cross-tenant denial tests across every endpoint, MCP tool, exports, search, object storage and caches.
- Fresh installation, restarts with retained data, migration/upgrade and complete backup/restore.
- UI E2E for onboarding, source setup, recorder evidence, question result, MCP settings, and the six-group question catalog. Visual regression at desktop and mobile against the supplied design.
- English/German coverage, keyboard navigation, focus handling and accessible labels.
- Optional extraction prompt-injection tests if AI extraction is implemented.
- Dependency/secret checks and a reproducible benchmark with hardware, dataset, concurrency and latency/lag measurements.

The earlier 50-tenant/250,000-entry workload remains a development smoke profile. The binding performance contract now includes a required 10-million-entry release benchmark and a separate 100-million-entry capacity experiment: benchmarks/performance-contract.json and specs/PERFORMANCE-ARCHITECTURE.md. Proposed reference targets include p95 hot order-state API latency <= 50 ms and p95 hot MCP tool latency <= 150 ms under the specified load, with correct committed-cutoff semantics and bounded memory. Measure cold reads, history, aggregate queries, durable acknowledgement, lag and restart separately. These are engineering acceptance targets, not achieved performance claims. Unavailable reference hardware means not run/blocked, not passed; a smaller validated release must not claim 100-million-entry capacity without that experiment. Keep reports/performance.json with raw evidence. Never weaken durability, authorization, accuracy or data shape to obtain a faster result.

Provide a local aggregate verification command and GitHub Actions. Run meaningful checks and fix failures. For unexecutable checks, record precise reasons and instructions to reproduce. Do not disable tests, weaken tenant policies, or edit the acceptance oracle to turn a failing result green.
